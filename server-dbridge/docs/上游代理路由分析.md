# 客户端连接时桥如何选择上游代理

## 结论

桥本身**不做路由决策**，上游代理信息是由**认证中心根据客户端的账号密码下发的**。

核心机制：客户端提供的用户名/密码就是"路由键"。桥把这对凭据提交给中心服务器认证，中心返回"该账号应该走哪个上游代理"的完整信息，桥只负责照做。

## 完整流程

### 1. 接入与协议识别

`internal/proxy/server.go` 的 `dispatch` 通过偷看连接的第一个字节判断协议：

- 首字节为 `0x05` → 按 SOCKS5 处理
- 否则 → 按 HTTP 处理

### 2. 提取客户端凭据

- **HTTP**：从 `Proxy-Authorization: Basic ...` 头解析用户名密码（`internal/proxy/http.go` 的 `parseProxyAuth`）
- **SOCKS5**：通过 RFC 1929 用户名/密码握手获取（`internal/proxy/socks5.go` 的 `handshake`）

### 3. 认证并获取上游信息（关键步骤）

`internal/auth/authenticator.go` 的 `Authenticate` 依次检查：

1. **IP 封禁**（Guard）
2. **失败缓存**：同一凭据最近失败过 → 直接拒绝
3. **成功缓存**：命中则直接复用之前拿到的上游信息，不再请求中心
4. 未命中 → 调用中心服务器 `/api/open/bridge/auth`（`internal/center/client.go` 的 `Authenticate`），请求附带 `BridgeID`/`BridgeSecret`、客户端凭据和客户端 IP

中心返回的 `AuthResponse` 就是路由结果：

| 字段 | 含义 |
| --- | --- |
| `Protocol` | 上游协议："http" 或 "socks5" |
| `IP` / `Port` | 上游代理地址 |
| `ProxyUser` / `ProxyPass` | 访问上游用的凭据 |
| `SpeedLimit` | 该账号的限速（0 表示使用默认值） |

也就是说：**账号 → 上游代理的映射关系完全由中心服务器维护**，桥是无状态的转发节点。

### 4. 转换为上游并建连

`authResponseToUpstream`（`internal/proxy/http.go`）把响应转成 `Upstream` 结构（`internal/upstream/dialer.go`），然后：

- **`Pool.Acquire`**（`internal/upstream/pool.go`）：以 `协议://用户:密码@地址` 为 Key 在连接池中登记，并施加：
  - 活跃上游数量上限（`MaxProxies`）
  - 单个上游并发连接上限（`MaxConnsPerProxy`）
  - 基于令牌桶的带宽限速器（`SpeedLimit`，为 0 时取 `DefaultSpeedLimit`）
- **`Pool.Dial` → `Dial`**（`internal/upstream/dialer.go`）：按上游协议走 SOCKS5 握手或 HTTP CONNECT，用中心下发的 `ProxyUser/ProxyPass` 向上游认证，最终打通到客户端请求的目标地址

### 5. 双向转发

`forward.Relay`（`internal/forward/relay.go`）在客户端连接与上游打出的连接之间做双向转发。

## 流程图

```
客户端
  │  (HTTP / SOCKS5 连接，携带用户名密码)
  ▼
桥: dispatch 识别协议 → 提取凭据
  │
  ▼
Authenticator.Authenticate
  ├─ IP 封禁检查 (Guard)
  ├─ 失败缓存检查
  ├─ 成功缓存命中 → 直接返回上游信息
  └─ 调用中心 /api/open/bridge/auth
        │
        ▼
     中心服务器返回 AuthResponse
     (Protocol / IP / Port / ProxyUser / ProxyPass / SpeedLimit)
  │
  ▼
authResponseToUpstream → Pool.Acquire (限速 + 并发控制)
  │
  ▼
Pool.Dial: SOCKS5 或 HTTP CONNECT 打通上游 → 目标地址
  │
  ▼
forward.Relay: 客户端 ⇄ 上游双向转发
```

## 补充说明

- **同一账号的所有连接都走同一个上游**：映射由凭据决定，且成功缓存让相同凭据直接复用结果。
- **桥不感知目标地址的选择逻辑**：客户端请求的目标（HTTP CONNECT 的 host、SOCKS5 的 target）只决定"上游之后连哪里"，不决定"用哪个上游"。
- **中心不可达时**：认证返回 `ErrUnavailable`，桥对客户端返回 503（HTTP）或 SOCKS5 拒绝，不做兜底路由。

## 涉及文件

| 文件 | 职责 |
| --- | --- |
| `internal/proxy/server.go` | 单端口监听，按首字节分发 HTTP / SOCKS5 |
| `internal/proxy/http.go` | HTTP/CONNECT 代理处理，提取凭据 |
| `internal/proxy/socks5.go` | SOCKS5 协议处理，RFC 1929 认证握手 |
| `internal/auth/authenticator.go` | 认证流程编排（封禁/缓存/中心调用） |
| `internal/center/client.go` | 与中心服务器的 HTTP 通信 |
| `internal/upstream/pool.go` | 上游连接池、并发限制、限速 |
| `internal/upstream/dialer.go` | 通过上游代理拨号到目标 |
| `internal/forward/relay.go` | 双向流量转发与流量统计 |
