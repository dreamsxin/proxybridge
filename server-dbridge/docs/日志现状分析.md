# 日志现状分析：格式、类型与完备性评估

## 一、日志基础设施

日志由 `cmd/dbridge/logger.go` 统一管理，格式与输出方式如下：

| 项目 | 现状 |
| --- | --- |
| 日志库 | 标准库 `log/slog`，全局 `slog.SetDefault` |
| 格式 | `slog.TextHandler`（key=value 文本），如 `time=2026-08-28T10:00:00.000+08:00 level=INFO msg="proxy listening" addr=:7890` |
| 级别 | `debug` / `info` / `warn` / `error`，通过 `[log].level` 配置，默认 `info` |
| 输出 | `[log].file` 有值时写文件，为空时写 stdout |
| 切割 | 按大小切割（`max_size_mb`，默认 100MB），旧文件重命名为 `xxx.20060102-150405.000000000` |

配置示例（`config.toml`）：

```toml
[log]
level = "info"
file = "logs/dbridge.log"
max_size_mb = 100
```

## 三、完备性评估：不完备，核心业务链路几乎无日志

现有日志只覆盖进程启动/退出和后台任务错误，而一条客户端请求的完整链路（接入 → 认证 → 选上游 → 拨号 → 转发 → 关闭）没有任何一条日志。具体缺口：

1. **连接/请求零记录**：客户端连接建立、协议识别、目标地址、所选上游、转发字节数、连接时长全部无日志。出问题时无法回答"这个客户端流量去了哪"。

2. **安全事件静默**：认证失败、IP 封禁（`Guard.IsBanned` / `Guard.RecordFailure` 触发封禁）、失败缓存命中都不打日志，无法做安全审计和暴力破解溯源。

3. **限流事件静默**：`ErrTooManyProxies` / `ErrTooManyConns` 触发时只返回客户端 503，服务端无感知。

4. **上游拨号失败静默**：`Pool.Dial` 的错误仅转化为客户端响应（502 / SOCKS5 拒绝），排查上游故障没有依据。

5. **中心配置刷新失败被吞掉**：`internal/center/config.go` 的定时拉取 `_ = m.fetch()` 失败无任何日志。

6. **缺少关联字段**：没有连接 ID / 请求 ID，各模块日志无法串联到同一条连接。

7. **切割策略不完整**：只按大小切割，无保留文件数量上限（可能撑爆磁盘）、无压缩。

8. **细节问题**：
   - `slog.Debug("socks5 reply", "rep", rep)` 中 `rep` 是裸数字，可读性差（应转为名称）；
   - `dispatch` 读首字节失败时静默关闭连接。

## 四、建议补充的日志类型

| 类型 | 建议级别 | 建议字段 |
| --- | --- | --- |
| 连接接入 | Debug | conn_id, client_ip, protocol |
| 认证成功 | Info | client_ip, upstream（脱敏） |
| 认证失败/封禁 | Warn | client_ip, reason（banned / fail_cache / auth_failed） |
| 限流拒绝 | Warn | upstream_key, reason |
| 上游拨号失败 | Warn | upstream, target, err |
| 连接结束 | Info/Debug | conn_id, target, bytes, duration |
| 中心配置刷新失败 | Warn | err |

## 五、结论

- **格式层面**：统一使用 `slog` + TextHandler，级别可配、输出可切、按大小切割，基础设施合格；建议后续增加 JSON 格式选项、切割文件数量上限与压缩。
- **覆盖层面**：日志类型集中在生命周期与错误兜底，**业务链路（认证、路由、转发、限流）完全缺失**，不满足生产环境排障与安全审计要求，建议按第四节的方案补全。
