# bridge-direct 运作流程分析

这是一个 **TCP 端口转发（桥接）中转服务**：在本机监听若干"桥端口"，把进来的 TCP 流量双向透传到指定的目标 `ip:port`，并通过一个加密的管理 API 动态增删转发规则。

## 整体架构

```
客户端 ──TCP──▶ :桥端口 ──io.Copy 双向透传──▶ 目标 ip:port
                    ▲
管理端 ──POST(AES加密)──▶ :5678 /bridge/add | /bridge/del   （仅 remote 模式）
                    │
启动时 ──POST──▶ syncDomain /api/notify/bridges   拉取桥列表（仅 remote 模式）
                    │
持久化 ──▶ bridge.db（文本文件，格式：端口,目标地址）
```

## 模块结构

| 模块 | 文件 | 职责 |
|---|---|---|
| 入口 | `main.go` | 命令行参数、配置加载、日志初始化、启动服务 |
| 配置 | `config/config.go` | 全局配置结构（模式、地址、密钥、数据文件等） |
| 服务 | `server/server.go` | 启动流程、管理 API（增删桥）、中心同步 |
| 转发 | `server/bridge.go` | 动态 TCP 监听管理与双向透传 |
| 数据 | `cachef/cachef.go` | 桥规则的文件持久化缓存 |
| 工具 | `utils/aes.go`、`utils/https.go` | AES-CBC 加解密、HTTP 客户端封装 |

## 启动流程（main.go）

1. 通过 `-c` 指定配置文件（默认 `config.json`），用 viper 读取并反序列化到 `config.Cfg`
2. 初始化日志（slog + lumberjack 滚动，支持级别/格式/文件配置）
3. `go server.Start()` 启动服务，主协程阻塞等待 `SIGINT` 退出

### 配置项说明（config.json）

| 字段 | 说明 |
|---|---|
| `mode` | `local` / `remote`，决定运行形态 |
| `addr` | 管理 API 监听地址（仅 remote 模式生效） |
| `syncDomain` | 中心同步服务地址（仅 remote 模式生效） |
| `key` | AES 加密密钥（长度须为 16/24/32 字节） |
| `dataFilename` | 桥规则持久化文件（如 `bridge.db`） |
| `bridgeId` | 本桥在中心端的标识，同步时使用 |
| `logFile` / `logLevel` / `logFormat` / `logSource` | 日志配置 |

## 核心流程（server.Start()）

分四步，**行为由 `mode` 决定**：

1. **打开缓存文件** — `cachef.New(dataFilename)` 打开 `bridge.db`，逐行解析 `端口,地址` 记录（支持 `1000:1010,1.2.3.4:80` 端口区间写法，见 `cachef.unmarshal`）
2. **同步桥列表**（仅非 `local` 模式）— `syncBridge()` 携带 `bridgeId` POST 到 `syncDomain + /api/notify/bridges`，返回 200 时**清空本地缓存**并用返回的桥列表重建
3. **恢复监听** — `InitBridgeHandler()` 遍历缓存中所有记录，逐个 `AddBridgeHandler` 建立 TCP 监听
4. **启动管理 HTTP 服务**（仅非 `local` 模式）— gin 监听 `addr`（默认 `:8080`），注册 `/bridge/add`、`/bridge/del`

> 即 **`local` 模式**：纯静态，只按本地 `bridge.db` 做转发，不对外提供管理接口；**`remote` 模式**：可被中心端同步 + 通过 API 动态管理。

## 转发流程（server/bridge.go）

每条规则对应一个动态监听：

- `listenProxy(port, toAddr)`：在 `:port` 上 `net.Listen`，注册进 `runListens` map（带锁防重复监听），Accept 循环中每个连接起一个协程处理
- `handlerBridge(conn, toAddr)`：`DialTimeout` 10 秒连目标，然后**两个方向各一个 `io.Copy`** 做全双工透传，并记录上下行流量日志（`[flow-up]` / `[flow-down]`）；任一方结束后关闭连接
- 生命周期管理：`Add/Change/Del BridgeHandler`，删除时关闭 listener 并等待 `done` channel 确认退出

## 管理 API 流程

### POST /bridge/add

1. `decryptReq`：取请求体 `data` 字段 → base64 解码 → **AES-CBC 解密**（密钥为配置的 `key`，IV 取密钥前 16 字节，见 `utils/aes.go`）→ 反序列化为 `{bridgePort, ip, port}`
2. `validateBridge`：校验桥端口、目标端口、IP 合法性（拒绝非法/未指定 IP）
3. 若该端口已存在 → `ChangeBridgeHandler`（先删后加）；否则 `AddBridgeHandler` 新起监听
4. `cf.Add` 持久化到文件；**持久化失败会回滚**（`DelBridgeHandler`）

### POST /bridge/del

解密 → 校验 `bridgePort` → `cf.Del`（从缓存和文件中移除）→ `DelBridgeHandler`（停止监听）。

### 请求/响应协议

请求体：

```json
{
  "ver": "版本号",
  "timestamp": 1716883200,
  "data": "base64(AES-CBC({\"bridgePort\":9000,\"ip\":\"1.2.3.4\",\"port\":80}))"
}
```

响应体：

```json
{ "code": 200, "msg": "ok", "data": null }
```

## 关键设计点

| 点 | 说明 |
|---|---|
| 持久化 | 自研文件缓存 `CacheF`：内存切片 + 每次写操作全量 `dump()` 重写文件，读写锁保护 |
| 安全性 | 管理接口请求体用 AES-128-CBC + PKCS5 填充加密（`Req{ver,timestamp,data}` 结构），防止明文被嗅探 |
| 恢复能力 | 重启后从 `bridge.db` 恢复所有转发监听；`remote` 模式启动时还会从中心端全量同步 |
| 热更新 | 同端口重复添加走"先停旧监听再建新监听"的替换逻辑，已建立的旧连接随 listener 关闭自然结束 |

## 一次典型请求时序（remote 模式新增桥）

```
管理端 ──加密{bridgePort:9000, ip:1.2.3.4, port:80}──▶ POST /bridge/add
   server: 解密 → 校验 → net.Listen(":9000") → 写缓存文件 → 返回 {code:200}
客户端 ──TCP──▶ :9000 ──拨号──▶ 1.2.3.4:80 ──双向 io.Copy──▶ 数据透传
```

## 总结

配置文件定义运行形态，缓存文件保证规则持久，中心同步 + 加密 API 负责规则的动态下发，核心就是一组可随时增删的 TCP 端口转发器。
