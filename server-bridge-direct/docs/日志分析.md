# bridge-direct 日志分析

结论：**日志不完备**。生命周期类日志（启动/增删监听/连接流量）较全，但**管理 API 的失败路径完全没有日志**、**中心同步失败完全静默**，且存在 `fmt.Println` 与 `slog` 混用、不进日志文件的问题。

## 一、现有日志清单

### 1. 生命周期 / 状态类（存在，较全）

| 位置 | 级别 | 内容 | 触发时机 |
|---|---|---|---|
| `main.go` L55 | Info | `bridge-direct started` + version | 启动完成 |
| `server/server.go` L43 | ⚠️ fmt | `Started Server Listen` + addr | 管理服务启动 |
| `server/bridge.go` L46 | Info | `AddBridgeHandler` port/toAddr | 新增监听 |
| `server/bridge.go` L38 | Info | `ChangeBridgeHandler` port/toAddr | 替换监听 |
| `server/bridge.go` L51 | Info | `DelBridgeHandler` port | 删除监听 |
| `server/bridge.go` L66 | Info | `listen` port/toaddr | 开始监听 |
| `server/bridge.go` L99 | Info | `close` port | Accept 循环退出 |
| `server/server.go` L111 | Info | `DelBridge` + bridge 结构 | 收到删除请求 |

### 2. 错误类（存在，但覆盖不全）

| 位置 | 级别 | 内容 | 覆盖场景 |
|---|---|---|---|
| `server/bridge.go` L32 | Error | `init bridge handler` port/toAddr/err | 启动时恢复监听失败 |

### 3. 流量类（存在，可能噪音大）

| 位置 | 级别 | 内容 |
|---|---|---|
| `server/bridge.go` L120 | Info | `[flow-up]` srcaddr/toAddr/amout |
| `server/bridge.go` L125 | Info | `[flow-down]` srcaddr/toAddr/amout |

每条连接 × 2 条，Info 级别，高并发下会刷爆日志。

## 二、缺失的日志（重点问题）

### ❌ 1. 管理 API 处理失败 —— 完全无日志

`AddBridge`（server/server.go L48-L93）的**所有失败分支**（解密失败、参数校验失败、监听失败、持久化失败回滚）都只返回 `HTTP {code:500, msg:...}`，服务端**一条日志都没有**。排查问题时无法从日志追溯谁在什么时候用错误参数调用了接口。

`DelBridge`（server/server.go L95-L132）同理：`cf.Del` 和 `DelBridgeHandler` 失败只回响应、不落日志。

### ❌ 2. 中心同步失败 —— 完全静默

`Start()`（server/server.go L28-L31）调用 `syncBridge()` 时**忽略了返回的 error**：同步域名不可达、HTTP 非 200、响应解析失败、`code != 200` 全部无声无息，且无重试。这是最危险的盲区。

### ❌ 3. 其他缺失

- `handlerBridge` 拨号失败日志缺 `toAddr`/`srcaddr`，多桥并存时无法定位是哪个桥失败
- `dump()` 无错误处理（`Truncate`/`Write` 失败不返回也不记录）
- 管理 API 无接入日志（gin `Default()` 的 Logger 中间件输出到 stdout，**不进 slog/日志文件**）

## 三、格式与类型问题

| 问题 | 具体表现 |
|---|---|
| **双轨输出** | `fmt.Println` 与 `slog` 混用：`server/server.go` L43、`server/bridge.go` L30、cachef 中多处（`dump` 每写一条打印一行、`unmarshal` 每行打印、`BatchAdd` 打印整个切片）。这些输出**不经过日志级别过滤，也不会写入 `logs/bridge.log` 和轮转归档** |
| **字段命名不一致** | `toaddr` vs `toAddr`（bridge.go L66 vs L46）；`amout` 是 `amount` 拼写错误（L120/L125） |
| **消息风格混乱** | 有的用函数名当 msg（`AddBridgeHandler`），有的用方括号标记（`[flow-up]`），有的用短语（`init bridge handler`） |
| **级别使用不当** | 每连接流量日志用 Info（应为 Debug）；`syncBridge` 响应体用 Debug 却配了个永不触发的失败静默 |
| **格式可切换** | `logFormat: text/json` 已支持，text 为 `key=value`、json 为结构化对象，但现有字段不规范导致两种格式都难解析 |

## 四、建议的统一规范

```
格式：<ts> <level> <source> msg=<事件> port=9000 toAddr=1.2.3.4:80 srcaddr=... err=...
```

1. **错误必落日志**：所有 `return err` 前补 `slog.Error(msg, "err", err, 上下文...)`；`AddBridge`/`DelBridge` 失败分支、`syncBridge` 错误必须记录
2. **消灭 `fmt.Println`**：全部改 `slog.Debug`，让其受级别控制并可进文件
3. **统一字段名**：`port`（桥端口）、`toAddr`（目标）、`srcaddr`（来源）、`err`（错误），修正 `amout` → `amount`
4. **流量日志降为 Debug**，或按采样/汇总输出
5. **管理 API 加请求日志**（来源 IP、耗时、结果码），替换或桥接 gin 默认 Logger
